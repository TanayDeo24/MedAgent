# JD_CAPABILITY_MATRIX.md

Machine-readable form: `artifacts/audit/jd_capability_matrix.json`. All
citations to git-history commit `14a59b9` unless noted.

| Capability | Status | Evidence |
|---|---|---|
| Search-based QA | **DIRECTLY DEMONSTRATED** | `main.py` CLI accepts a natural-language query; `agent/graph.py`'s 6-node pipeline returns a synthesized report with citations (`agent/nodes.py:956-1111`). |
| Heterogeneous-source retrieval | **DIRECTLY DEMONSTRATED** | `tool_execution_node` (`nodes.py:563-734`) can call PubMed, ClinicalTrials.gov, and ChEMBL in the same run, and `synthesis_node`/`report_generation_node` cross-reference across them — e.g. `_build_chembl_compound_table` (`nodes.py:225-315`) matches a ChEMBL compound to a ClinicalTrials.gov NCT ID by intervention-name substring match, a real cross-source synthesis mechanism, not just parallel independent calls. |
| Text processing | **DIRECTLY DEMONSTRATED** | `retrieval/chunking.py` (word-based chunking, 180/30 default, with title-prefixed embedding text per `retriever.py:142`); `tools/pubmed_tool.py` parses NCBI XML via `xml.etree.ElementTree`. |
| Information retrieval | **DIRECTLY DEMONSTRATED** | `retrieval/retriever.py`: dense FAISS search, sparse BM25 search, Reciprocal Rank Fusion (`_rrf_fuse`, retriever.py:205-232, standard k=60 formula), cross-encoder reranking (`_rerank`, retriever.py:121-151). Measured on 3 distinct labeled eval sets (`retrieval/eval_set*.json`) with recorded Recall@10 numbers (`retrieval/eval_results_*.json`, 19 files) — real IR evaluation, not just implementation. |
| Semantic understanding | **PARTIALLY DEMONSTRATED** | Dense embeddings (`all-MiniLM-L6-v2`, `index_meta.json`) provide semantic (not just lexical) matching; `query_analysis_node`'s structured extraction (targets/diseases/compounds/query_type) is LLM-based classification, not a dedicated NLU model — "the LLM does it" without a separate demonstrated NLU technique beyond prompting. |
| NLU (query understanding) | **PARTIALLY DEMONSTRATED** | `QUERY_ANALYSIS_PROMPT` (`prompts.py:18-58`) performs structured slot extraction (drug targets, diseases, compounds, query type classification into 6 categories, constraints) — a real, concrete NLU task, but implemented entirely via LLM prompting with JSON output, no separate NER/intent-classification model or evaluation of extraction accuracy exists. |
| ML | **PARTIALLY DEMONSTRATED** | Uses pretrained ML models directly (sentence-transformer embeddings, cross-encoder reranker, LLM) — no model is trained/fine-tuned in this repo. Legitimate "ML systems integration," not "ML research/training." |
| RAG | **DIRECTLY DEMONSTRATED** | Full pipeline: corpus build (`retrieval/build_corpus.py`) → chunk (`chunking.py`) → embed+index (`build_index.py`, FAISS) → BM25 (`build_bm25.py`) → hybrid retrieve+rerank (`retriever.py`) → wired into generation (`nodes.py:794-806, 1044-1051`). A genuine, measured, iterated-on RAG system (3 index variants tried: base, chunk_256_50, chunk_384_64, per `data/index/variants/`), not a stub. |
| Source-aware retrieval | **DIRECTLY DEMONSTRATED** | Citations distinguish live-API PubMed results from RAG-index PubMed passages under different labels (`"PubMed"` vs `"PubMed RAG"`, `nodes.py:993-1028`) — provenance is explicitly tracked, not conflated. |
| Biomedical query understanding | **PARTIALLY DEMONSTRATED** | Domain-specific prompt engineering (MeSH-term guidance in `TOOL_QUERY_GENERATION_PROMPT`, prompts.py:157-160; target/indication distinction for ChEMBL); no biomedical-specific NER model (e.g. no scispaCy/BioBERT) is used — domain awareness lives entirely in prompt text. |
| Evidence-grounded generation | **DIRECTLY DEMONSTRATED** | Every generation prompt (`SYNTHESIS_PROMPT`, `REPORT_GENERATION_PROMPT`) explicitly instructs grounding only in `tool_results`/`retrieved_context` and forbids external knowledge (prompts.py:222, 425); the compound table is generated deterministically in Python specifically to remove LLM discretion over what's asserted as fact (`nodes.py:225-315`). |
| Citation grounding | **PARTIALLY DEMONSTRATED** | Citations are mechanically built from real tool/RAG data (not LLM-invented, `nodes.py:987-1030`), but there is no automated check that a specific inline citation in the prose actually supports the specific claim next to it — grounding is enforced by prompt instruction + deterministic data assembly, not verified per-claim. |
| Retrieval-relevance evaluation | **DIRECTLY DEMONSTRATED** | Recall@10 measured across 3 eval-set designs (survey/strict/grounding) and multiple pipeline configurations (dense/hybrid/BGE-embedding/chunk-size/HyDE/weighted-RRF), with an oracle-ceiling analysis (`PHASE3_RETRIEVAL_QUALITY_COMPLETE.md` §10-12) — genuine, rigorous IR evaluation methodology, even though the absolute numbers are modest (0.40-0.66, not 0.92). |
| Answer-quality evaluation | **PARTIALLY DEMONSTRATED** | `AgentEvaluator._check_task_success` (`evaluator.py:548-605`) is a real, codified multi-criterion success check; LLM-judge hallucination detection exists (`hallucination_judge.py`) but its own docstring and `RESULTS.md` document it as unreliable (~39% judge success rate) and explicitly "not the rigor of human verification." |
| Tool reliability | **PARTIALLY DEMONSTRATED** | `tool_precision` metric is real and measured (85.3%/76.8%), but no metric tracks raw API call success/failure rate as such; hallucinated tool-name selection is tracked (`nodes.py:603-626`) and shown to still occur (9 distinct hallucinated tool names across 60 cases, `RESULTS.md` "Tool-hallucination counting" note). |
| Workflow reliability | **PARTIALLY DEMONSTRATED** | Real incident response exists (90-min hang found and fixed with hard timeouts + incremental persistence + resume, `EVAL_HANG_FIX_COMPLETE.md`; a live Metal/MPS concurrency crash found and fixed, `RESULTS_RAG_COMPARISON.md` §2) — strong evidence of debugging real production-shaped failures, but overall task success rate remains 18-38% measured, i.e. the *workflow* is not itself highly reliable at its stated task. |
| Production-aware latency | **PARTIALLY DEMONSTRATED** | Latency is measured and reported honestly including anomalies (`RESULTS.md` latency-anomaly root-cause section); no caching layer beyond per-tool in-memory TTL cache (`tools/base_tool.py:100-133`) and no async/concurrent external-API calls within a single case (only case-level concurrency across independent evaluation runs, `evaluator.py:340-393`). Per-case latency (~178-210s average) is not production-grade for interactive use. |
| Failure handling | **DIRECTLY DEMONSTRATED** | Every node wraps its LLM call in try/except with a degraded fallback (`nodes.py`, all 6 nodes); `BaseTool._execute_with_monitoring` (`base_tool.py:135-240`) standardizes tool-level error handling; documented real failure modes (503/429/502/timeout/JSON-parse-failure) are caught and counted, not silently swallowed (`RESULTS.md` "Failure characterization"). |
| Reproducibility | **PARTIALLY DEMONSTRATED** | Evaluation runs are versioned and incrementally persisted with resume support (`evaluator.py:113-146, 197-307`) and methodology is documented in detail (`RESULTS.md`, `RESULTS_RAG_COMPARISON.md`) — strong practice — but this audit could not independently re-run the pipeline (no verified live `NVIDIA_API_KEY`, and the working tree currently has no source code to execute at all, see `INITIAL_STATE.md` §1), so none of the headline numbers were independently reproduced, only traced to their originating artifact. |

## Overall

Of 19 capabilities assessed: **7 DIRECTLY DEMONSTRATED**, **10 PARTIALLY
DEMONSTRATED**, **0 NOT DEMONSTRATED**, **0 fully UNVERIFIED** (evidence
existed one way or another for every capability, even where the underlying
metric was weak). This is a materially stronger evidentiary picture than the
target-claim list in `CLAIM_EVIDENCE_MATRIX.md` alone would suggest — the
project's core *engineering* (architecture, tool integration, retrieval
pipeline, honest evaluation methodology) is real and substantial; it is
specifically the **headline marketing numbers** (96%, 98%, 5K+, 0.92, 0.88,
~5%, ~35%, ~0.91) that are fabricated or unsupported, not the underlying
system.
